Round 04 · Talk

What's a PR
in the age of
agentic engineering?

If code alone isn't enough — and an agent can write a thousand lines before lunch — what do we actually commit, and what are we really reviewing?

The thing we've all seen
The PR
nobody can review

A vibecoded pull request: 2,000 lines, and no one — not even the author — can say what it does or why it's built that way. Agents make code cheap, so PRs sprawl. The reviewer is left rubber-stamping a wall of plausible diff.

Over to you
Ever hit "approve" without really following it?

Be honest. A wall of AI-generated changes, a deadline, and no thread to pull. What did you actually check — and what did you just trust?

The shift
The diff is no longer
the valuable part

When code is cheap to generate and cheap to regenerate, the diff stops being the artifact worth guarding. What's scarce now is intent — what we meant, why it's shaped this way, and the proof it holds together. A PR has to carry that, not just the code.

The answer
So what do
we commit?

The PR ships the requirements that justify the code: the spec (what & why), the plan (architecture), the task list (how it was broken down) — and the code that satisfies them. Its purpose flips from "read this diff" to "prove the code meets a contract you can read first."

The view · anatomy of the PR
PR #128 · passwordless login
specs/042-passwordless-login/
├─ spec.md          what & why — the contract
├─ plan.md          architecture & approach
├─ tasks.md         ordered task breakdown
└─ contracts/
   └─ auth-api.md   interfaces the code must honour

src/auth/
├─ login.ts          code — the artifact
└─ session.ts

tests/auth/
└─ login.test.ts     proves the contract holds

The requirements artifacts live beside the code, in the same PR — there to support it, not in a wiki nobody opens.

Who reviews it, and how
Read top-down,
not diff-first
  • spec.md — is this the right thing? (product / domain owner)
  • plan.md — is it built the right way? (tech lead / architect)
  • tasks.md — is it complete, nothing skipped? (reviewer)
  • the diff — does the code match the contract? (reviewer + tests)
Over to you
Would this have saved your worst review — or just slowed it down?

Picture your last messy PR shipped with a spec, a plan, and a task list beside the code. Genuinely better — or ceremony you'd skip?

Where this leaves us
The PR becomes
the contract

Not a diff to rubber-stamp, but a small, reviewable case that the right thing was built the right way. The code is the artifact; the spec, plan, and tasks are the argument. That's what we commit now.
